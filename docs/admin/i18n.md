# Internationalisation (i18n)

Ce document décrit le système de traduction de l'admin web, l'initialisation côté client et serveur, et le mécanisme de synchronisation de la langue avec l'URL.

---

## Configuration (`services/i18n.ts`)

```ts
{
  supportedLngs: ["en", "fr"],
  fallbackLng: "en",
  defaultNS: "common",
  ns: ["common", "auth", "validation", "navigation"],
  react: { useSuspense: false },
}
```

| Clé | Valeur | Description |
|---|---|---|
| `supportedLngs` | `["en", "fr"]` | Langues acceptées par l'application |
| `fallbackLng` | `"en"` | Langue utilisée si la locale demandée est absente |
| `defaultNS` | `"common"` | Namespace utilisé quand `t("clé")` est appelé sans namespace explicite |
| `ns` | voir ci-dessous | Namespaces chargés au démarrage |
| `react.useSuspense` | `false` | Désactive Suspense pour i18next - les composants ne se suspendent pas pendant le chargement des traductions |

**Namespaces :**

| Namespace | Contenu |
|---|---|
| `common` | Textes partagés : nom de l'app, erreurs génériques, états de chargement |
| `auth` | Pages de connexion, inscription, mot de passe |
| `validation` | Messages d'erreur des formulaires |
| `navigation` | Labels de la navigation et des menus |

## Fichiers de traduction

Les fichiers JSON sont placés dans le dossier public et servis statiquement :

```
public/
└── locales/
    ├── fr/
    │   ├── common.json
    │   ├── auth.json
    │   ├── validation.json
    │   └── navigation.json
    └── en/
        ├── common.json
        ├── auth.json
        ├── validation.json
        └── navigation.json
```

- **Côté client** : chargés via HTTP depuis `/locales/{{lng}}/{{ns}}.json` (`i18next-http-backend`).
- **Côté serveur** : lus depuis le système de fichiers `./public/locales/{{lng}}/{{ns}}.json` (`i18next-fs-backend`).

Les fichiers sont identiques - seul le mode d'accès diffère selon l'environnement.

## Initialisation côté client (`entry.client.tsx`)

L'initialisation i18next est effectuée **avant** l'hydratation React. Le rendu du DOM ne commence qu'une fois `i18n.init()` résolu, ce qui garantit que les traductions sont disponibles dès le premier rendu.

```
window.requestIdleCallback(hydrate)   // priorité basse si disponible
  ou window.setTimeout(hydrate, 1)    // fallback
```

L'hydratation est déclenchée pendant un temps d'inactivité du navigateur pour ne pas bloquer les interactions critiques au chargement.

**Plugins utilisés :**

| Plugin | Rôle |
|---|---|
| `initReactI18next` | Intégration React (hook `useTranslation`, composant `Trans`) |
| `LanguageDetector` | Détection automatique de la langue |
| `Backend` (http) | Chargement des fichiers JSON via HTTP |

**Ordre de détection de la langue :**

```ts
detection: { order: ["path", "localStorage", "htmlTag"] }
```

1. Segment de chemin URL (`/fr/...`) - prioritaire, cohérent avec le routing.
2. `localStorage` - langue mémorisée d'une session précédente.
3. Attribut `lang` du tag `<html>`.

## Initialisation côté serveur (`entry.server.tsx`)

Le serveur crée une **instance i18next distincte par requête** via `createInstance()`. Il n'y a pas d'état partagé entre les requêtes, ce qui évite tout risque de contamination de langue entre utilisateurs.

La langue est lue directement depuis l'URL - pas de `LanguageDetector` côté serveur :

```ts
const segments = url.pathname.split("/");
const lng = i18nConfig.supportedLngs.includes(segments[1])
  ? segments[1]
  : i18nConfig.fallbackLng;
```

**Stratégie de rendu SSR :**

| Type de client | Option React | Comportement |
|---|---|---|
| Bot (détecté par `isbot`) | `onAllReady` | Attend le rendu complet avant d'envoyer la réponse - meilleur pour le SEO |
| Utilisateur normal | `onShellReady` | Envoie le shell dès qu'il est prêt, stream le reste - meilleur pour le temps de chargement perçu |

Un timeout de **5 secondes** (`ABORT_DELAY`) interrompt le rendu si le serveur ne répond pas à temps.

## Synchronisation de la langue avec l'URL

Le hook `useLanguageSync` est appelé dans le layout racine à chaque changement de route :

```ts
// root.tsx
const { lang } = useParams();
useLanguageSync(lang);
```

**Logique interne :**

```
useLanguageSync(lang) :
  lang absent ou i18n non initialisé  ->  no-op
  langue déjà correcte                ->  no-op
  changement déjà en cours vers lang  ->  no-op  (protection doublons via ref)
  sinon                               ->  i18n.changeLanguage(lang)
```

Une `ref` (`isChangingTo`) mémorise la langue cible en cours de changement. Cela évite d'appeler `changeLanguage` plusieurs fois pour la même langue si le composant se re-rend pendant la transition (ex : navigation rapide).

## Utilisation dans les composants

**Hook `useTranslation` :**

```ts
// Namespace par défaut (common)
const { t } = useTranslation();
t("appName");

// Namespace explicite
const { t } = useTranslation("auth");
t("login.title");

// Plusieurs namespaces
const { t } = useTranslation(["auth", "validation", "common"]);
t("login.title");                           // auth (premier de la liste)
t("required", { ns: "validation" });        // validation
t("internalServerError", { ns: "common" }); // common
```

**Composant `Trans` pour le HTML inline :**

Utilisé sur la page d'inscription pour les liens dans les CGU :

```tsx
<Trans
  i18nKey="register.termsAndConditions"
  ns="auth"
  components={{
    1: <a href="#" className="link" />,
    3: <a href="#" className="link" />,
  }}
/>
```

**Locale dans les meta :**

Les exports `meta` utilisent `i18n` directement (pas le hook) car ils s'exécutent hors du cycle React :

```ts
export const meta: MetaFunction = () => [
  { title: i18n.t("login.metaTitle", { ns: "auth" }) },
];
```

## Locale et appels API

La locale courante est **automatiquement injectée** sur tous les appels via l'intercepteur Axios (voir [auth.md](auth.md)). Il n'est pas nécessaire de passer manuellement `?locale=` dans les composants.

Pour désactiver l'injection sur un appel spécifique, utiliser le header `X-Skip-Locale: true`.
